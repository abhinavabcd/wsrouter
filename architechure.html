wsrouter

A guide to authentication, routing, shared quotas, connection recovery, and operation.

Client WebSocket→Authenticate and admit→Hash-ring owner→Destination sockets

The leader shares the ring snapshot. Each router owns a range of node IDs and maintains persistent peer WebSockets for remote delivery. Feedback follows the same route back to the source. The leader is a membership dependency; this design does not provide unlimited capacity or durable delivery.

wsrouter

A Go WebSocket router with a consistent hash ring. All production code is in main.go. Tests live in tests/; tests/router.go links to the production source so the suite can exercise private internals without maintaining a copy. Authentication uses HTTPS verifiers, and every node ID contains its authentication domain. There is no shared signing secret or locally signed token.

Run

All advertised addresses, verifier requests, and peer connections use HTTPS/WSS with certificate verification enabled. The listening port comes from --addr, defaulting to 443. Omitting --clusteraddr starts a leader. Give servers unique, well-spaced ring positions between 0 and 9223372036854775807.

go run . --addr=https://sub1.example.com:8443 --ssl_certs=/path/to/certs --id=0
go run . --addr=https://sub2.example.com:8443 --ssl_certs=/path/to/certs \
  --clusteraddr=https://sub1.example.com:8443 --id=4611686018427387904

The certificate directory should contain a matching .pem certificate chain and .key private key. fullchain.pem/privkey.pem and public.pem/private.pem are also supported. Each server must trust the certificates used by its peers and authentication authorities. See local HTTPS testing for mkcert and automated test fixtures. The container image installs system CA certificates; a local CA must also be trusted inside the container.

Create and connect

POST /create accepts these required fields:

{"auth_domain":"auth.example.com","path":"/verify","secret_string":"opaque-secret"}

Example response:

{"node_id":"auth.example.com|0123456789abcdef0123456789abcdef","token":"/verify|opaque-secret","address":"https://sub1.example.com:8443"}

auth_domain is a hostname with an optional port, without a scheme or path. path starts with / and can include query parameters. The first | separates the path from the secret, so the secret may contain additional | characters. Creation generates a candidate node ID and verifies it before returning credentials. A denied, invalid, or unavailable verifier response returns HTTP 401 without credentials. The external authority must already recognize the supplied secret and decide which node IDs it permits.

Connect to /connect using URL-encoded node_id and token query parameters. Non-browser clients can instead send X-Node-ID and Authorization: Bearer TOKEN. Both identity and token are required. The router sends:

POST https://auth.example.com/verify?node_id=auth.example.com%7C0123456789abcdef0123456789abcdef
Content-Type: application/json

{"node_id":"auth.example.com|0123456789abcdef0123456789abcdef","secret":"opaque-secret"}

The verifier must return HTTP 200 with JSON:

{"verified":"auth.example.com|NODE_RANDOM_ID","rp5":10,"maxc":5}

verified must exactly equal the requested node_id. Legacy valid responses are rejected. maxc is an optional positive integer, defaulting to 5, that limits tracked /connect sockets per node. A new connection evicts and closes the oldest tracked socket when the limit is reached. A lowered limit evicts as many oldest sockets as needed before tracking the new one. Eviction is an intentional close and does not replay recent packets. rp5 is required and must be a positive integer. Plain ok, missing or mismatched verified, invalid rates, redirects, certificate failures, and timeouts deny authentication. Verification has a five-second timeout and an 8 KiB response limit. The node_id query parameter always comes from the requested identity, replacing any existing values. Other query parameters are preserved, except action, which is controlled by the router.

The verifier can additionally return x_src_id and expires (Unix seconds). Without them, x_src_id defaults to the node ID and validity is decided by the authority on each authentication. A returned expiry must be in the future. /create no longer accepts trusted identity, rate, or lifetime claims from the caller: the authority supplies them. Old HMAC tokens are incompatible with this protocol.

GET /locate takes the same credentials, verifies them, and returns the ring owner's address. /connect returns HTTP 421 and {"address":"https://owner:port"} if the node belongs elsewhere. Browser WebSocket APIs cannot read that response body, so browser clients should use /locate before connecting. WebSocket origins from any domain are accepted. /create and /connect (along with the other HTTP endpoints) return Access-Control-Allow-Origin: * and answer CORS preflight requests. If an incoming request includes Origin, the router forwards it unchanged as the Origin header on its HTTPS verification request, including lookup and renewal. The authority can approve or deny that origin through its verified response. Requests without Origin leave it absent. /create also forwards Origin and checks approval before returning credentials.

Renewal

POST /renew takes the same node ID and token. The receiving server calls the verifier directly with action=renew, without looking up or proxying to the ring owner. Only an approving JSON response allows renewal. That server then disconnects any local sockets for the node and returns its identity, token, and verifier-provided policy. Sockets on other servers remain connected. Denied renewal leaves existing sockets connected.

An authority can return secret_string in its renewal response to rotate the credential. The router returns the existing path combined with that new secret. Without a replacement secret, the token stays the same. The authority must recognize the new secret and revoke the old one when rotation is intended; the router cannot mint credentials for an external backend. A verifier may approve renewal after its own expiry policy has denied normal connections, returning a fresh future expires value if it uses that field.

Cluster authentication

Each process generates a local random secret and uses advertised-host[:port]|ring-position as its node ID and /server|local-secret as its token. A follower POSTs server_domain, id, and secret to the primary's /server endpoint. The primary checks the domain relationship and calls the joining server's HTTPS /server?node_id=... endpoint with JSON containing node_id and secret. That endpoint approves only the process's own identity and secret, using the same JSON response format. Registration also runs during the minute membership refresh, allowing a restarted process to register its new credential.

An authenticated authority matching the server's hostname or permitted parent domain identifies a server node. For sub1.example.com, the parent is example.com; for sub1.x.y.com, it is x.y.com. Siblings and descendants of that parent are trusted after HTTPS verification. Public suffixes such as co.uk and github.io are excluded using the public suffix list. IP addresses and localhost use exact hostname matching; ports do not change domain ownership.

The primary distributes server credentials in HTTPS ring snapshots. GET /snapshot from the TCP source 127.0.0.1 returns an unauthenticated text table (addr, nodes, ringid) for local inspection, without credentials in the output. Forwarded IP headers do not grant access. The local node count is live; remote counts reflect the last ring refresh. POST /snapshot updates still authenticate the configured primary, and /peer WebSocket upgrades require a registered server ID, matching credential, and successful HTTPS verification. Membership changes are pushed immediately; epochs and versions order updates. Servers disappear from the ring after three minutes without refresh. The primary must remain available for joins and ring refreshes.

Server nodes can supply their own src_id, src_node_id, x_src_id, timestamp, and status messages. Those fields pass through unchanged. Regular nodes have source identity assigned by the router and cannot send status packets.

After replacing certificate files, POST /reload on that server with its own server node ID in X-Node-ID and its local server token in Authorization: Bearer TOKEN. A successful reload returns 204 and updates new TLS connections; existing sockets remain open. Invalid files return 502 and retain the previous certificate. These administrative credentials are available to trusted cluster members through the ring snapshot; they are never logged or exposed by /health.

Messages and delivery

Send JSON text frames with string payloads. Base64-encode binary data when needed:

{"_id":"message-1","type":"data","dest_node_id":"auth.example.com|destination-id","payload":"AP8="}

Use dest_node_ids for fanout (1–1,024 destinations), or dest_node_id for one destination, but not both. Each copy has one dest_node_id, preserves the same _id, and routes to every eligible connection for that destination. Missing or empty _id values are generated. Hashing includes the whole domain-prefixed node ID.

Each connection receives a router-assigned socket ID. If a packet targets its own source node, it skips the socket that issued it and reaches the node's other connections. This applies to single-destination sends, fanout including self, and replay. Generated status feedback still reaches the originating socket. A self-send with no other eligible connection receives status: failed.

The source socket ID is internal metadata: client-supplied src_socket_id cannot override it, and it is not included in application packets. Peer frames preserve it so a packet returning to the same router still skips its origin. New sockets get new IDs even after the node's last connection closes. Older peers ignore this optional metadata; replay through an older peer cannot preserve this exclusion.

Regular nodes may provide an integer Unix millisecond timestamp between the server's receive time minus 8,000 milliseconds and its current time, inclusive. A missing/null timestamp is filled by the server. An invalid time produces type: "drop", payload: "invalid_time", with the other input fields copied. Server nodes preserve supplied timestamps without drift checks. Replay preserves the original ID and timestamp.

The authority's rp5 limits each regular node across all its WebSockets using shared fixed server-time buckets (UnixMilli / 5000). One incoming packet consumes one allowance, including invalid timestamps and fanout requests. Excess traffic gets type: "drop", payload: "rate_limited". Dropped packets are returned only to that socket and are not routed. Server nodes bypass these limits.

Delivery feedback uses the same ring:

{"_id":"message-1","type":"status","payload":"success","dest_node_id":"auth.example.com|sender-id","src_node_id":"auth.example.com|destination-id","src_id":"auth.example.com|destination-id"}

success means a destination connection accepted the packet into its send queue. An unavailable destination or forwarding failure produces payload: "failed". Feedback identifies the original receiver in src_node_id and legacy src_id, so correlate by src_node_id plus _id.

Servers ping client sockets every TCP_KEEP_ALIVE seconds (default 30), overridable through tcp_keep_alive on /connect. Server connections default to 3 seconds. A socket that does not answer closes after a further ten seconds. Packets sent toward a client socket during its keepalive window are rerouted on unexpected disconnect before deciding failure. Peer links retain the last three seconds of packets in both directions and replay them on disconnect. Replays preserve _id and stop after three attempts. Older receipts are retained for ten seconds and fail only when the destination remains locally owned and has no connections.

A shared cleanup job scans active histories and recent receipts; there is no timer per idle node. Replay is best effort and can create duplicates. Process crashes lose in-memory queues. success is an enqueue notice, not a final delivery guarantee.

Packets must contain valid UTF-8 JSON. Routing fields (_id, source IDs, x_src_id, and each destination ID) are limited to 1,024 bytes; type is limited to 128 bytes. Invalid envelopes close that socket. If adding canonical fields would make a drop reply exceed 1 MiB, the socket closes instead of emitting an oversized reply. Peer batches accept at most 32 frames and reject invalid hop/replay metadata. An empty membership snapshot cannot replace a live ring. /create and /refresh require one complete JSON value, rejecting trailing data.

Blocking/unblocking is client-owned: those type names have no special router behavior. rp5 is shared per node and counts each incoming packet once; fanout consumes one allowance, not one per destination. Queue byte caps remain in effect.

Packets are limited to 1 MiB. Each client has a 1,024-packet send queue capped at 4 MiB. Incoming fanout is expanded into bounded shared routing queues: 4 MiB of pending work per source connection and 128 MiB per server. Routing uses up to eight workers, chosen from GOMAXPROCS, and consistently assigns a destination node to a worker. Connection lifecycle and replay cleanup retain their locks. Slow/full client queues close the socket; a full peer queue returns a routing failure instead of blocking a worker.

Client read buffers up to 64 KiB are reused across messages; larger buffers are released before waiting for more input. Peer data and feedback use separate queues that grow on demand, each capped at 64 MiB. Feedback is prioritized with regular data turns to avoid starvation. New peers negotiate X-Peer-Batching: 1; queued JSON frames may then share a WebSocket message, with up to 32 newline-separated frames per batch and no deliberate batching delay. Legacy peers continue using one JSON frame per message. Read and batch-write buffers are reused per peer.

The hash ring is published as an immutable routing snapshot. Existing peer connections bypass dial locks; new dials are serialized per peer. Client pings use one heap scheduler/timer per server, while socket writes remain in their writer goroutines. Replay records reference immutable packets and expiry releases old references. Byte limits cover queues, not all retained replay payloads or total process memory. /health reports routing/feedback errors, ring size, and distinct local nodes. See PERFORMANCE.md for measurements and limitations.

The full ring snapshots and single membership coordinator impose practical scaling limits; this system is not infinitely scalable or coordinator fault tolerant.

Tests

go test -race ./... # Go 1.25+; production builder currently uses Go 1.27.3
WSROUTER_STRESS=1 go test -run TestStressFiveServers -count=1 -v -timeout=10m ./tests

Tests use trusted local TLS certificates with hostname verification enabled. The stress test starts five HTTPS servers and 1,000 WSS clients, 200 created through each server. Every client sends to the other 999, mixing fanout and individual packets. It waits for 999,000 data packets and 999,000 success statuses, checking identity and deduplicating replay. The verifier supplies rp5: 1000 for these clients. Set WSROUTER_STRESS_NODES=50 for a smaller run.

Reproduce the controlled performance runs with the Dockerfile's Go image:

./stress_test.sh                         # three 1,000-node all-to-all runs
RUNS=0 WSROUTER_STEADY=1 ./stress_test.sh # 40 seconds of sustained traffic

The runner defaults to four CPUs, GOMAXPROCS=4, and 6 GiB container memory. Override CPUS with an integer, MEMORY, RUNS, or WSROUTER_STRESS_NODES as needed. The sustained test uses 100 clients, 1 KiB payloads, about 5,000 messages/second, and the default 30-second replay window. It reports success-feedback p50/p99, sampled heap, and allocations. Both tests include the load generators in the same process as the five test routers; these results are not production capacity limits.

Malformed-input regressions cover JSON syntax/type errors, null envelopes, oversized IDs and messages, invalid UTF-8, deep nesting, bad fanout, peer metadata/batches, and normal closure during a fragmented message. Run the bounded parser fuzz test with go test -run '^$' -fuzz FuzzPacketEnvelope -fuzztime=30s ./tests.

Node state retention

Successful WebSocket authentication updates the shared node's rp5 without resetting its bucket counters. All sockets for that node share the allowance; fanout consumes one allowance. Server connections retain their admission bypass.

The last WebSocket close retains node state for at least 10 seconds. Reconnecting during retention reuses its counters. Socketless state is excluded from connected node counts and is unavailable for delivery. A single cleanup goroutine uses a min-heap, one reusable timer, and a buffered wake channel. Each socketless node has at most one pending check; later closes extend its deadline. Cleanup retains active nodes and rechecks object identity before deleting expired state.

HTTPS domain authentication migration

Implemented in main.go. Node connections, renewal, cluster registration, snapshots, and peer forwarding use the HTTPS authority protocol below. Shared-secret signing has been removed.

Protocol

POST /create accepts:

{"auth_domain":"auth.example.com","path":"/verify","secret_string":"opaque-secret"}

It returns node_id: "auth.example.com|<random-id>" and token: "/verify|opaque-secret". The domain is a hostname with an optional port; it does not include a scheme or path. The verification path begins with / and may include query parameters. The token splits at its first |, allowing additional delimiters in the secret.

Clients supply both node_id and token to /connect, /locate, and /renew. Browser clients use URL-encoded query parameters. Other clients may use X-Node-ID and Authorization: Bearer TOKEN headers.

Authentication sends:

POST https://auth.example.com/verify?node_id=auth.example.com%7C0123456789abcdef0123456789abcdef
Content-Type: application/json

{"node_id":"auth.example.com|0123456789abcdef0123456789abcdef","secret":"opaque-secret"}

An incoming Origin header is forwarded unchanged to the verifier; if absent, no Origin header is added. The authority decides whether that origin is permitted. This also applies to lookup and renewal, including renewal at a non-owner server. /create supports CORS from any domain and verifies the generated candidate node ID and supplied secret before returning credentials. Denied, invalid, or unavailable verification returns HTTP 401.

The JSON body contains node_id and secret. The node ID is also retained in the query for compatibility. Existing node_id query values are replaced; other parameters are preserved. The router controls the action query parameter, adding action=renew for renewal and removing it for ordinary authentication.

Approval requires HTTP 200 and JSON:

{"verified":"auth.example.com|NODE_RANDOM_ID","rp5":10,"maxc":5}

verified must exactly equal the requested node_id. Legacy valid responses are rejected. maxc is an optional positive integer, defaulting to 5, that limits tracked /connect sockets per node. A new connection evicts and closes the oldest tracked socket when the limit is reached. A lowered limit evicts as many oldest sockets as needed before tracking the new one. Eviction is an intentional close and does not replay recent packets. rp5 must be a positive integer and becomes the node's shared allowance per five-second bucket across all its WebSockets. Plain ok, missing or mismatched verified, missing or invalid rates, redirects, certificate failures, and timeouts deny authentication. Requests have a five-second timeout and responses are limited to 8 KiB.

The verifier also supports optional x_src_id and expires (Unix seconds) from the authority. Without them, source identity defaults to node_id, and validity is decided by the authority at each authentication. Renewal can return secret_string to rotate the token; otherwise it approves the existing token. The router cannot independently mint a new secret that an external authority will recognize.

Server registration

SERVER_SECRET and cluster_secret have been removed. Each process generates a local random secret and uses:

node_id = advertised-host[:port]|ring-position
token   = /server|local-random-secret

The joining server calls POST https://<primary>/server with JSON server_domain, id, and secret. The primary must verify both the permitted domain relationship and the credential by POSTing JSON containing node_id and secret to the joining server's HTTPS /server?node_id=.... A supplied domain name alone does not prove control. The joining server's listener must be available before registration.

The local /server verifier approves only its own node ID and random secret, returning the required JSON. Successful registration distributes the server credential in the ring snapshot over HTTPS. Peer upgrades must match a registered ring identity and pass HTTPS verification. Snapshots must authenticate the configured primary; certificate reload must authenticate the local server credential.

An authenticated node is a server when its authority is the current server hostname, its permitted parent, or a descendant of that parent. For sub1.x.y.com, that parent is x.y.com. The public suffix list prevents widening trust to com, co.uk, or shared hosting suffixes such as github.io. Hostnames are compared on label boundaries. Ports do not change domain ownership. IP addresses and localhost use exact hostname matching.

Renewal authenticates directly through the authority with action=renew on whichever server receives the request, then disconnects that node's local sockets. It does not depend on ring ownership or proxy to another router; sockets on other servers remain connected. Rate limits and identity fields come from the authority response. Existing signed tokens require migration to the new node ID and token pair.

Local HTTPS tests

Automated tests use Go's httptest.NewTLSServer and its certificate-trusting client. Certificate verification stays enabled; an ordinary client without the test trust rejects the same server. This runs without installing a CA or needing mkcert in CI. See Go's httptest documentation.

The current tests cover JSON POST bodies, query preservation, repeated node_id replacement, mandatory JSON validity, authority-provided rp5, renewal responses, rejected redirects and certificates, malformed credentials, sibling domains, nested parent domains, unrelated domains, public suffixes, and IP addresses.

The routing fixtures use a local test certificate for *.router.test and auth.client.test. HTTPS listeners run on loopback while the client validates each advertised hostname. Tests cover registration proof, forged registration denial, primary-only snapshots, authenticated WSS forwarding, renewal disconnection, and routing behavior. The five-server/1,000-node stress test uses the same verified TLS fixtures; its authority returns rp5: 1000.

For manual testing, mkcert can create locally trusted certificates:

mkcert -install
mkdir -p /tmp/wsrouter-certs
mkcert -cert-file /tmp/wsrouter-certs/server.pem \
  -key-file /tmp/wsrouter-certs/server.key \
  localhost 127.0.0.1 ::1 sub1.router.test sub2.router.test auth.client.test

Map the three .test hostnames to 127.0.0.1 in local DNS or /etc/hosts, and use separate HTTPS ports. Give each router --ssl_certs=/tmp/wsrouter-certs and the corresponding advertised HTTPS URL. The auth fixture must use auth.client.test so it remains outside the trusted server parent domain. Containerized processes need the mkcert root certificate in their own trust store; the root is rootCA.pem in the directory reported by mkcert -CAROOT. No insecure TLS option is needed.
